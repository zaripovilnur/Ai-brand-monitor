# Мониторинг бренда в ответах ИИ

Внутренний инструмент маркетинговой команды YADRO. Прогоняет набор вопросов через несколько
ИИ-моделей, размечает ответы и показывает динамику по неделям.

Не коммерческий продукт. Работает локально, на машине пользователя. Пользователь — маркетолог,
не программист: объясняй решения простыми словами и не предлагай ему править код руками.

## Порядок работы

1. Сначала прочитай `prototype/ai-brand-monitor.jsx` — это утверждённый прототип интерфейса.
   Вся вёрстка, тексты, состав экранов и логика метрик уже согласованы. Переноси их как есть,
   не переизобретай.
2. Отличие от прототипа одно: данные должны приходить из настоящего API, а не из генератора.
   Функции `runEngine` и `compose` — заглушки, их надо заменить.
3. Не меняй формулировки на экранах без спроса. Тексты выверены.

## Стек

- Фронтенд: React + Vite + TypeScript, стили инлайновые как в прототипе, графики — recharts,
  выгрузка — SheetJS (`xlsx`)
- Бэкенд: Node.js + Express, тот же репозиторий, папка `server/`
- База: SQLite через `better-sqlite3`, файл `data/app.db`. Никаких внешних БД
- Запуск: `npm run dev` поднимает фронт и бэк одновременно (`concurrently`)

Одна команда для старта, никаких докеров и миграционных фреймворков.

## Ключ и безопасность

- Ключ AITunnel лежит **только** в `.env` на бэкенде, переменная `AITUNNEL_API_KEY`
- `.env` в `.gitignore` с первого коммита
- Браузер никогда не получает ключ. Экран «Подключение» показывает последние 4 символа,
  которые отдаёт бэкенд отдельным полем
- Все вызовы моделей идут через бэкенд, фронт ходит только в свой `/api/*`

## Шлюз AITunnel

- Base URL: `https://api.aitunnel.ru/v1`, формат OpenAI Chat Completions
- Заголовок: `Authorization: Bearer sk-aitunnel-...`
- Один ключ на все модели, включая модель-судью. Отдельной интеграции для судьи нет
- Обязательно передавать `max_tokens` — по нему резервируется стоимость
- В ответе приходит `usage.cost_rub` — сохраняй в базу, показывай фактическую стоимость прогона
- Судья вызывается с `response_format: { type: "json_schema", json_schema: { strict: true, ... } }`
- Ограничений по частоте у шлюза нет, но `429` прилетает от провайдеров: пауза 200–300 мс между
  запросами, до 3 повторов с экспоненциальной задержкой

Запрещено, потому что ломает сопоставимость замеров:

- модель `auto` и плавающие алиасы «последней версии» — только точные строки моделей
- запасные модели (fallback) — в отчёт попадут ответы не той модели
- любое изменение промпта судьи без увеличения его версии

## Модели

Строки моделей хранятся в базе и правятся на экране «Подключение», а не в коде.
Стартовые значения — из прототипа. Перед первым прогоном сверь их с каталогом шлюза.

## Схема данных

```
brands      id, name, aliases, competitors
facts       id, brand_id, text
prompts     id, brand_id, text, category, category_auto, active, version
runs        id, brand_id, started_at, finished_at, models, repeats, judge_model,
            judge_prompt_version, mode ('parametric'), cost_rub, status
answers     id, run_id, prompt_id, model, repeat, raw_response (JSON), text,
            latency_ms, cost_rub, error
marks       id, answer_id, mention, position, accuracy, tone, strength,
            evidence, note, judge_error
```

Сырой ответ модели сохраняется всегда. Это позволяет переразметить архив после правки промпта
судьи, не тратя деньги на повторные запросы к моделям.

`runs` хранит слепок настроек целиком: без него через три месяца никто не поймёт, откуда взялись
цифры, и нельзя будет понять, какие прогоны сравнимы.

## Категории запросов

Определяются автоматически по тексту, правила проверяются сверху вниз, любую можно
переопределить вручную (тогда `category_auto = false`):

1. есть алиас бренда → `brand`
2. есть маркер замещения (заменить, альтернатива, вместо, импортозамещ, аналог) → `competitive`
3. есть маркер подборки (какие компании, какие производители, лучшие, подходят, выпускают,
   производят) → `category`
4. иначе → `info`

## Метрики

Ставятся на каждый ответ. Первые две считает код, остальные — модель-судья.

| Метрика | Значения | Кто считает |
|---|---|---|
| Факт упоминания | есть / нет | код: поиск по алиасам |
| Позиция | первым / в середине / в конце | код: сравнение индексов вхождений |
| Точность | точно / частично точно / неверно | судья, сверка с базой фактов |
| Тональность | без оценки / нейтральная / позитивная / негативная / смешанная | судья |
| Сила рекомендации | просто упоминает / советует наравне / явно рекомендует / не рекомендует | судья |

Правила расчёта долей:

- факт упоминания — от всех ответов прогона
- остальные метрики — только от ответов с упоминанием
- точность — только от упоминаний с проверяемым утверждением о компании
- сила рекомендации не усредняется: «не рекомендует» это не низший балл, а другое направление.
  Показывается распределение
- на брендовых запросах факт упоминания, позиция и сила рекомендации не считаются: бренд назван
  в самом вопросе. Там имеют смысл точность, тональность и неузнавание

## Модель-судья

- Отдельный вызов на каждый ответ, после сохранения ответа в базу
- Дешёвая модель, обязательно не совпадающая с проверяемыми
- `temperature: 0`, версия модели логируется в прогон
- Судья **не получает** название модели, давшей ответ — иначе появится систематическое смещение
- Возвращает `evidence` (фрагмент ответа) и `note` (одно предложение) — они показываются
  пользователю в разборе «Как посчитано». Без них команда не доверяет оценкам
- Значение вне перечня или сломанный JSON → один повтор, затем метка «не размечено».
  Подставлять значение по умолчанию нельзя: молчаливый нейтрал испортит статистику

Текст промпта хранится в базе, редактируется на экране «Подключение», версионируется.
Стартовый текст — в `server/prompts/judge.txt`.

## Прогон

Долгая операция: 12 запросов × 3 модели × 3 повтора = 108 вызовов плюс столько же вызовов судьи.

- Запускается через `POST /api/runs`, выполняется в фоне
- Фронт опрашивает `GET /api/runs/:id` и показывает прогресс
- Ошибка на одном ответе не роняет прогон: пишется в `answers.error`, остальное продолжается
- Прогон можно продолжить после сбоя, не начиная заново

## Порядок разработки

Не пиши всё сразу. По шагам, каждый проверяется вживую:

1. Каркас проекта, `.env`, SQLite, один эндпоинт `GET /api/health`
2. `POST /api/test-model` — один запрос к одной модели, ответ показывается на экране.
   **Стоп-точка: убедиться, что ключ работает и модели отвечают**
3. `POST /api/test-judge` — разметка одного вставленного вручную текста.
   **Стоп-точка: проверить, что судья возвращает валидный JSON по схеме**
4. Бренд, факты, запросы с автоклассификацией — CRUD и экраны из прототипа
5. Полный прогон с очередью, прогрессом и сохранением
6. Дашборд, лента ответов, выгрузка в Excel — перенос из прототипа на реальные данные

После каждого шага останавливайся и объясняй, что проверить руками.

## Первый прогон

Начинай с 2 запросов × 1 модель × 1 повтор. Это несколько рублей. Убедись, что данные дошли до
дашборда, и только потом увеличивай.
